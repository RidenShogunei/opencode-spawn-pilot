## 1. 研究背景与动机

### 1.1 为什么要研究 Subagent Spawn？

在大模型应用中，Multi-Agent 协作已经成为提升复杂任务能力的常见手段。常见的范式是：

```
Main Agent ────(delegate)────> Sub Agent (搜索/工具执行)
     │                              │
     │<────(return results)─────────┘
     ↓
  整合答案
```

**核心问题**：Subagent 真的返回了吗？返回的东西被主模型用上了吗？

### 1.2 已有研究的问题

- 大多数 Multi-Agent 论文关注"准确率提升"，忽略了 **spawn 失败** 和 **return 失败** 的情况
- 没有系统地对比：单 Agent vs 强制多 Agent vs 模型自主决定多 Agent 三种模式
- 缺乏对 subagent 返回机制的深入分析（是否真的注入了？主模型真的用了？）

### 1.3 本研究目标

1. 系统对比三种 Agent 协作模式在多跳问答任务上的表现
2. 验证 subagent spawn + return 机制的可靠性
3. 分析 spawn 机制在不同复杂度任务（2/3/4 hop）上的效果差异
4. 找出 spawn 机制的真正瓶颈：是搜索失败还是推理失败？

## 3. 实验设计

### 3.1 三种 Agent 协作模式

```
┌─────────────────────────────────────────────────────────┐
│                    Single Agent                          │
│  模型独立完成所有搜索 + 推理，无委托                      │
└─────────────────────────────────────────────────────────┘

┌─────────────────────────────────────────────────────────┐
│               Force-Multi (强制多 Agent)                 │
│  每次工具调用都强制通过 task 工具 spawn subagent         │
│  prompt 中明确告知："你必须使用 task 工具搜索"           │
└─────────────────────────────────────────────────────────┘

┌─────────────────────────────────────────────────────────┐
│              Agent-Decides (模型自主决定)                │
│  模型自由决定是否使用 task 工具 spawn subagent           │
│  prompt 中告知："你可以使用 task 工具委托搜索"           │
└─────────────────────────────────────────────────────────┘
```

### 3.2 评估指标

| 指标 | 定义 |
|------|------|
| **Accuracy** | 正确回答数 / 总题数 |
| **Spawn Rate** | 模型决定 spawn 的比例（FM 固定 100%，AD 实际比例） |
| **Subagent Return Rate** | spawn 后 subagent 返回结果的比例 |
| **Spawn Accuracy** | spawn 的任务中正确回答的比例 |
| **Non-Spawn Accuracy** | 未 spawn 的任务中正确回答的比例（仅 AD） |

### 3.3 核心假设

- **H1**：Force-Multi 的 spawn 率应接近 100%（强制委托）
- **H2**：Subagent 返回率应接近 100%（内部机制保证）
- **H3**：3-hop 和 4-hop 任务从 spawn 中获益更多（搜索空间更大）
- **H4**：如果 spawn 后准确率仍低，说明瓶颈在推理而非搜索

## 4. OpenCode 工具架构

### 4.1 工具层次

```
Main Model (Qwen3.5-9B)
    │
    ├── Bash / Edit / Replace / View / Glob / Grep
    │   (直接执行，原生工具体验)
    │
    └── Agent tool (task 委托)
            │
            └── Subagent Model (独立 Qwen3.5-9B 实例)
                    │
                    ├── GlobTool (只读)
                    ├── GrepTool (只读)
                    ├── LS (只读)
                    └── View (只读)
```

**关键限制**：Subagent 无法使用 Bash/Edit/Replace，只能搜索和读取。

### 4.2 Prompt 传递机制（重要发现）

```
┌──────────────────────────────────────────┐
│ Step 1: 写入 prompt 文件                  │
│   SYSTEM_SINGLE (系统提示)               │
│   + 任务内容                              │
│   → .prompt_*.txt                        │
└──────────────────────────────────────────┘
              ↓ 写入文件
┌──────────────────────────────────────────┐
│ Step 2: 模型接收到的上下文                │
│   OpenCode CoderPrompt (内置系统提示)     │
│   + 模型自己调用 read 工具读取 prompt 文件 │
└──────────────────────────────────────────┘
              ↓ read tool call
┌──────────────────────────────────────────┐
│ Step 3: 模型执行任务                      │
│   模型先调用 read 获取完整 prompt         │
│   然后执行推理 + 工具调用                  │
└──────────────────────────────────────────┘
```

**发现**：模型必须主动调用 read 工具获取 prompt，不是直接接收。

### 4.3 task 工具的 JSONL 输出（重要 bug）

```
正常工具调用 JSONL 事件流：
  step_start → tool_use (bash/grep...) → tool_result → step_finish → text

task 工具调用 JSONL 事件流：
  step_start → tool_use (task) → [缺少 tool_result!] → step_finish → text
                 ↑
                 OpenCode binary v1.3.6 不输出 task 工具的 tool_result 事件
                 subagent 结果被注入到 context，但不出现在 JSONL 输出中
```

## 6. 实验结果

### 6.1 总体结果

| 模式 | 准确率 | Spawn 率 | Subagent 返回率 |
|------|--------|----------|---------------|
| **Single Agent** | **23/55 (41.8%)** | 0% | — |
| **v14 Force-Multi（baseline）** | 22/55 (40.0%) | 33/55 (60%) | 100% |
| **v13 Force-Multi（Deliberation）** | 25/55 (45.5%) 人工 | 33/55 (60%) | 100% |

> ⚠️ **说明**：v13 的自动评测为 0%（extract_answer bug），45.5% 为人工逐题核查结果。v14 修复了 extract_answer 后自动评测正常工作。
>
> ⚠️ **数据修正**：v14 的 subagent 返回率 100% 基于"事件索引法"检测（task 工具调用后有后续事件 = subagent 返回），之前关键词搜索方法完全失效。

**关键发现**：
- v13 Deliberation 提示词使准确率提升 5.5%（45.5% vs 40%），但 spawn 率未变
- v14 baseline 与 Single 基本持平（差 -1 题）
- 所有 spawn 的 subagent 都返回了（100%），但返回不等于答对

### 6.2 Per-Hop 准确率（v14 vs Single）

| Hop | 题数 | Single | v14 Multi | Spawned 准确率 | 胜负 |
|-----|------|--------|-----------|---------------|------|
| 2-hop | 20 | 35% (7/20) | **50%** (10/20) | 47% (7/15) | Multi +3 |
| 3-hop | 15 | 40% (6/15) | **53%** (8/15) | 56% (5/9) | Multi +3 |
| 4-hop | 14 | **36%** (5/14) | 21% (3/14) | 25% (2/8) | Single +4 |

**观察**：
- 2-hop 和 3-hop：Multi 略优于 Single，但绝对差异不大（3 题）
- 4-hop 和 Hotpot：Multi 显著劣于 Single
- Hotpot 是 Multi 最大的失败场景：6 题中 Single 对 5 题，Multi 只对 1 题

## 7. 结果分析

### 7.1 为什么 v13 Deliberation 提示词有效？

v13 在基础 Force-Multi prompt 上增加了"先思考再 spawn"步骤：

```
- First, read the question and think about what information is needed and where to find it
- Then spawn at least one subagent using task(...)
```

结果显示 spawn 率不变（60%），但 spawn 后准确率从 v14 的 47%（2-hop）提升到 v13 的更高水平。**可能原因**：Deliberation 让模型在 spawn 前多了一步"规划"，减少了"过早委托"（Premature Delegation）现象。

### 7.2 为什么 Hotpot 是 Multi 的重灾区？

5/6 的 Hotpot 任务 Multi 输出为空（output_len=0）。这不是准确率问题，而是**输出捕获 bug**。Multi 的 v14 实现使用 `script -q -c '...' /dev/null | tee` 捕获输出，部分任务出现了 0 字节输出（可能是 PTY 交互时序问题）。Single 没有使用 `script`，因此没有这个问题。

这是一个工程问题，不是 spawn 机制的问题。

### 7.3 为什么 4-hop 是 Single 更好的临界点？

4-hop 任务中，Multi spawn 率仅 57%（8/14），且 spawn 后准确率只有 25%（2/8）。**可能原因**：

1. **推理链太长**：4-hop 推理链需要 4 步，spawn-return 循环每多一次，上下文错误累积的概率就增加
2. **Subagent 工具集太弱**：subagent 只能用 Glob/Grep/LS/View，无法执行复杂搜索
3. **主模型整合能力不足**：9B 模型处理 4-hop 推理本身已经吃力，再加 spawn 的 overhead 更难

### 7.4 为什么 Subagent 返回后仍然答错？

即使 subagent 返回了结果（token delta 证明），主模型的最终回答仍然经常是错的。

**可能原因**：

1. **推理链整合失败**：subagent 返回的是原始搜索结果（如 "B 的 CEO 是 X"），主模型需要自己推理如何用这个信息，但推理能力不够。

2. **Agent 工具限制**：subagent 只能 Glob/Grep/LS/View，无法执行 Wikipedia 页面深度解析。

3. **Context 注入格式**：subagent 返回的是纯文本，主模型需要自己决定哪些部分有用。

4. **返回时机错误**：subagent 返回的内容时机不对，主模型已经在错误的推理路径上走了太远。

## 8. 发现与讨论

### 8.1 意外发现：Binary JSONL Bug

**现象**：早期实验中所有 `subagent_returned = 0%`，但 token delta 证明 subagent 确实返回了。

**根因**：OpenCode binary v1.3.6 的 JSONL 输出**不包含** `tool_result` 事件。

```python
# 旧的（错误的）检测逻辑
for event in jsonl_events:
    if event['type'] == 'tool_result' and event['tool'] == 'task':
        subagent_returned = True  # 永远不触发！

# 新的（正确的）检测逻辑：事件索引法
task_event_index = None
for i, event in enumerate(events):
    if event.get('type') == 'tool_use' and event['part'].get('tool') == 'task':
        task_event_index = i

# 如果 task 工具调用后还有后续事件，说明 subagent 返回并被处理了
if task_event_index is not None and task_event_index < len(events) - 1:
    subagent_returned = True
```

**真实数据**：v14 中 33 次 spawn，所有 33 次后续都有后续事件（100% 返回）。

### 8.2 Prompt 传递机制验证

通过 15 次对照实验验证了 OpenCode 的 prompt 传递：

```
实验设计：
  对照组：直接发送 prompt
  实验组：通过 @prompt_file 传递

结果：实验组准确率更高 → 模型确实读取了 prompt 文件
```

首次工具调用始终是 `read` 工具调用，证明模型必须主动获取 prompt 内容。

### 8.3 模型对 Spawn 的态度

| 模式 | 实际 Spawn 率 | 解读 |
|------|---------------|------|
| Force-Multi（v14） | 60% (33/55) | 即使强制，也有 40% 没 spawn（可能是模型判断不需要） |
| Agent-Decides（v12旧数据） | 11% (6/55) | 模型很少自主决定 spawn |

**观察**：模型对 spawn 持保守态度，即使被告知"可以 spawn"也极少使用。这可能反映了模型对 subagent 机制的信任度不高。

### 8.4 核心发现：模型不懂如何正确地进行 Task Delegation

> **这是本研究的最重要的发现。** 60% 的 spawn 率中有大量委托是无效的，甚至是有害的。真正的瓶颈不在于 subagent 是否返回，而在于主模型根本不知道什么时候该委托、怎么委托、以及如何整合结果。

我们从实验日志中识别出三类典型的任务委托病态行为：

#### 病态 1：过早委托（Premature Delegation）

主模型还没完成问题理解和解题规划，就急着把任务甩给 subagent。

**日志实例**：
```
description: Search smooth jazz and artists
prompt: "Along with Kenny G and the performer of Hello Tomorrow, 
         what artist was featured on Smooth Jazz Stations?"
```

模型在 prompt 里直接复述了原问题，连自己都没想清楚要搜什么、怎么搜。这说明模型的内部流程是"生成 prompt → 立刻 spawn"而不是"先想清楚搜索策略 → 再委托"。

#### 病态 2：过度委托（Redundant Delegation）

问题已经快要解出，或者文档里已经有明确答案，模型仍然要 spawn 一下。

**日志实例**：
```
description: Find Amy Madigan's spouse and gun in Westworld
prompt: "From the documents provided, find information about Amy Madigan's 
         spouse and what gun that spouse used in the TV series Westworld."
```

这是 2-hop 简单问题，paragraph 里直接写了答案，但模型选择先 spawn 一轮"找 spouse"，再 spawn 一轮"找 gun"。对于这类问题，Single Agent 直接读文档可能只需要 3 步，而 Force-Multi 引入了一整个 spawn-return 循环的开销。

#### 病态 3：工具盲目（Tool Blindness）

主模型没有强制 subagent 使用任何工具，也没有指定要搜索的具体段落，导致 subagent 可能读了错误的文档或者用低效的方式搜索。

**日志实例**：
```
description: Search for César Gaytan birthplace
prompt: "Read the provided documents and find where César Gaytan was born 
         (which continent). Provide specific information about his birthplace."
```

prompt 里没有告诉 subagent 去哪个段落找，只说"读提供的文档"。subagent 实际用 Glob/Grep/LS/View 工具在文档中搜索，但主模型无法控制它的搜索路径。

#### 为什么这导致 spawn 有害？

| 病态类型 | 具体表现 | 对准确率的影响 |
|----------|----------|----------------|
| 过早委托 | 问题还没理解就委托，subagent 搜索方向可能偏了 | 主模型被错误信息误导 |
| 过度委托 | 简单问题也要走完整 spawn-return 链 | 开销大于收益，破坏推理链 |
| 工具盲目 | subagent 搜不到关键信息，或者搜到但主模型不知道 | 看似 spawn 了，实际没解决问题 |

**结论**：当前 9B 模型的任务委托能力远未成熟。Force-Multi 强制 spawn 实际上是在强迫一个不会 delegation 的模型去 delegation，结果是制造了大量无效委托和错误推理链。

## 9. 结论

### 9.1 核心结论

1. **Subagent spawn 机制工作正常** — 100% 返回（token delta 证明），但返回内容的可用性有限。

2. **Spawn 机制整体持平** — 在当前基准上，Single (41.8%) ≈ v14 FM (40.0%)，差 -1 题。

3. **Deliberation 提示词有正收益** — v13（Deliberation）比 v14（baseline）高 5.5%，但 spawn 率不变。

4. **2-hop 和 3-hop 是 spawn 可能有效的场景** — Multi 略优于 Single（2-hop +3 题，3-hop +2 题）。

5. **4-hop 和 Hotpot 是 spawn 无效的场景** — Single 显著优于 Multi（4-hop +4 题，Hotpot +4 题）。

6. **瓶颈在推理而非搜索** — subagent 找到了正确信息，主模型仍然推理错误。

### 9.2 与已有工作的差异

| 发现 | 已有预期 | 实际结果 |
|------|---------|---------|
| Spawn 率 | 强制模式应该 ~100% | 实际只有 60%（模型判断不需要时就不 spawn） |
| Return 率 | 应该有部分失败 | 实际 100% 返回 |
| Spawn 收益 | 复杂任务受益 | 简单 2-hop 反而受益最多，4-hop 受害 |
| 准确率提升 | Multi-Agent 应该更好 | 基本持平，收益被无效委托抵消 |

## 10. 未来工作

### 10.1 当前实验的局限

- 仅使用 Qwen3.5-9B，结论可能不适用于其他模型
- 仅使用 MuSiQue + HotpotQA 数据集
- Subagent 使用与 Main Model 相同的模型（Homogeneous），未测试异构模型组合
- Hotpot 任务的 0 字节输出问题需要工程修复

### 10.2 改进方向

**方向 1：改进 Subagent 返回格式**

当前 subagent 返回纯文本，主模型需要自己提取有用信息。未来可以：
- 让 subagent 返回结构化结果（JSON 格式）
- 让 subagent 提供推理步骤（而不只是搜索结果）

**方向 2：同义词扩展搜索**

OpenCode Agent 工具目前只有 Glob/Grep/LS/View，无法进行 Wikipedia 搜索。可以扩展工具集来提升搜索质量。

**方向 3：Main-Subagent 对话历史**

当前 subagent 是无状态的，每次调用都是全新的 context。可以引入对话历史让 subagent 理解主模型的完整推理链。

**方向 4：异构模型组合**

- Subagent 使用更小的 specialized 模型（如 Qwen2.5-0.5B 做搜索）
- Main model 使用更大的模型（如 Qwen3.5-9B 做推理）

**方向 5：更复杂的多跳基准**

MuSiQue 的 hop 数有限，可以测试 hop 数更高（5-hop+）的任务，看 spawn 机制是否在更复杂场景下效果更好。
