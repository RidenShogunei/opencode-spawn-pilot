## 一句话结论

> **Multi-Agent 的收益取决于「分工类型」，不取决于任务复杂度。**
>
> 让子代理做**推理**（reasoning）：+10.6pp ✅  
> 让子代理做**检索**（retrieval）：-4pp ❌

## 1. 研究问题

### 核心问题

> **小模型（9B）做 Multi-Agent 协作时，什么时候该 spawn 子代理？spawn 完之后怎么用结果？**

```
三个子问题：
├── When:  模型什么时候决定 spawn？会不会自愿 spawn？
├── How:   怎么给子代理写 prompt？分工怎么划分？
└── Use:   子代理返回结果后，主代理怎么整合？
```

### 已有研究的盲区

大多数 Multi-Agent 工作假设「spawn 就能提升」，但从未系统研究过：
- 小模型（9B）能否正确使用 spawn 机制
- Spawn 的收益到底来自什么（检索？推理？）
- Spawn 在什么条件下有害

## 2. 实验设计全貌

### 基准数据集

| 数据集 | Hop | 题数 | 特征 |
|--------|-----|------|------|
| MuSiQue | 2 | 82 | 可控多跳，文档 7-20KB |
| MuSiQue | 3 | 51 | 三步推理链 |
| MuSiQue | 4 | 56 | 四步推理链 |
| HotpotQA | 2 | 6 | 维基百科实体 |
| Large-scale | 2-4 | 6 | 大文档 47-53KB |
| **总计** | — | **195** | — |

### 实验环境

| 参数 | 值 |
|------|-----|
| 模型 | Qwen3.5-9B (主代理 + 子代理同一个模型) |
| 部署 | vLLM 0.19.1, GPU 2 |
| 上下文窗口 | 65,536 tokens（最大文档仅 13K tokens） |
| 框架 | OpenCode CLI，子代理通过 `task` 工具孵化 |
| 子代理工具 | grep, read, glob, ls（只读） |

### Agent 协作模式

```
模式 1: Single Agent — 模型直接读文档，不spawn（对照组）

模式 2: Force-Multi — 通过 prompt 指令要求模型 MUST spawn
         主代理 → task(description, prompt, subagent_type="general")
              → 子代理 grep/read 搜索
              → <task_result> 返回
         主代理 → 综合 → 最终答案

模式 3: Free Choice — 模型自由决定 spawn 还是直接读（v26-free）
```

## 3. 版本演进：17 个版本的探索之路

### 探索期：v12–v21（55题 → 195题）

| 版本 | 描述 | 准确率 | Spawn率 | 规模 |
|------|------|--------|---------|------|
| v12 | 最简 MUST 触发词 | 27% | 84% | 55t |
| v14 | Naive Force-Spawn | 27% | ~80% | 55t |
| v15 | Force-Spawn + 3步验证 | 40% | ~58% | 55t |
| v20 | FM 新基线 (97题) | 53% | 71% | 97t |
| v21 | **195题全量基线** | **51%** | **72%** | 195t |
| v21-single | Single 对照 | **51%** | 0% | 195t |

**v21 关键发现**：
- FM (51%) ≈ Single (51%)，整体持平
- **但 spawn 后的 141 题：FM 62% vs Single 51%，+10.6pp**
- 未 spawn 的 54 题：FM 22% vs Single 52%，**差了 30pp**

### Prompt 消融实验：v22–v25

| 版本 | 策略 | 效果 |
|------|------|------|
| v22 | COORDINATOR + NEVER/FORBIDDEN | ❌ 0% spawn，6题后终止 |
| v23 | 去掉 MUST 触发词，自然语言描述 | ❌ 20% spawn，10题后终止 |
| v24 | 还原 MUST + task，去掉验证步骤 | ✅ 47% acc，72% spawn，172题 |
| v25 | HTTP proxy 强制 tool_choice | ❌ finish_reason 级联失败，废弃 |

**Prompt 工程结论**：
- ✅ MUST + 工具名（"MUST use task tool"）→ 最佳触发
- ✅ 短 prompt (<400 chars) > 长 prompt
- ❌ 否定句（NEVER, FORBIDDEN）→ 0%
- ❌ tool_choice 代理强制 → 框架兼容性失败

### 关键实验：v26（195题全量）

| 版本 | 条件 | Spawn率 | 准确率 |
|------|------|---------|--------|
| v26-must | 文档在文件 + MUST 触发 | **84%** | **45.1%** |
| v26-single | 文档在文件 + 单 Agent | 3% | **49.2%** |
| v26-free | 文档在文件 + 自由选择 | **0%** | **80%** |

## 4. 核心发现：分工类型才是变量

### 关键对比：v21 vs v26

| | v21 (文档在 prompt 里) | v26 (文档在文件里) |
|---|---|---|
| Spawn 率 | 72% | 84% |
| FM 准确率 | 50.8% | 45.1% |
| Single 准确率 | 51.3% | 49.2% |
| **FM vs Single 净差** | **-0.5pp（持平）** | **-4.1pp（FM 更差）** |
| **Spawn 后准确率** | **61.7%**（强于 Single 51%） | **46.6%**（弱于 Single 48%） |
| 子代理做什么 | 主代理选段落 → 子代理推理 | 子代理读全文 → 检索+推理 |
| **分工类型** | **推理分工 ✅** | **检索分工 ❌** |

### 为什么会这样？

```
v21 (推理分工):
  主代理先读文档 → 选定相关段落
  → spawn 子代理，只给它相关段落
  → 子代理只做推理（从给定段落提取答案）
  → +10.6pp

v26 (检索分工):
  主代理不读文档
  → spawn 子代理，让它读全部 documents.txt
  → 子代理做检索（grep/read 全文档）+ 推理
  → 检索失败 → 说 "not found"
  → -4pp
```

**核心洞察**：Qwen3.5-9B 的瓶颈在**检索**，不在推理。让同一个 9B 模型去做检索（grep 关键词、扫读长文档），它做不好。但让它只做推理（给定相关段落后提取答案），它可以。

## 5. 子代理到底被派了什么活？完成得怎么样？

### 失败模式分布（107 次失败 / 195 题）

| 失败模式 | 数量 | 占比 | 说明 |
|----------|------|------|------|
| 🔴 **子代理没找到答案** | **52** | **49%** | 信息在文档里，grep 没命中 |
| 🟠 子代理找到了但整合出错 | 26 | 24% | 主代理误用/改写子代理结果 |
| 🟡 空输出/垃圾输出 | 11 | 10% | 模型崩溃 |
| 🟡 完全闲置（什么都没干） | 10 | 9% | MUST 强制副作用 |
| 🟡 直接读了但读错 | 7 | 7% | 没 spawn 自己读但推理错 |
| 🟢 评测假阴性 | 1 | 1% | 实际对了但评测判错 |

### 子代理任务类型

| 类型 | 占比 | 成功率 | 例子 |
|------|------|--------|------|
| 单步事实提取 | ~70% | 中 | "Read documents.txt and find X" |
| 多跳链式搜索 | ~20% | 低 | "First find X, then Y related to X..." |
| 验证任务 | ~10% | 很低 | "Verify the answer to..." |

## 6. 最震惊的数据：100% 检索失败

### 逐题核查结果

在 v26-must 中，24 例子代理明确说 "not found" / "not available" / "not contain"。

| 分类 | 数量 |
|------|------|
| 🟢 文档里确实没有，子代理判断正确 | **0 例** |
| 🔴 答案明确在文档里，子代理没找到 | **24 例** |

### 不是上下文窗口的问题

| | 数值 |
|---|---|
| vLLM max-model-len | 65,536 tokens |
| 最大文档 | ~53KB ≈ 13K tokens（20%） |
| 平均文档 | ~10KB ≈ 2.5K tokens（4%） |
| Prefix caching | ✅ 已开启 |

**文档远远小于上下文窗口。问题是搜索策略，不是容量。**

### 三个典型案例

**案例 A：答案在文档第 4 行，翻了 5 遍没看到**

- 任务：Jane Siberry 在哪出生？
- 答案：**Casa Loma**（出现在文档 Paragraph 1，第 4 行）
- 子代理行为：spawn 了 5 次，搜 "Jane Siberry birthplace" → 找到了专辑信息但没找到出生地
- 输出：*"Jane Siberry's birthplace is not available in these documents"*

**案例 B：枪名在段落标题里，搜错了关键词**

- 任务：Westworld 里出现的枪是什么？
- 答案：**LeMat revolver**（Paragraph 14 的标题）
- 子代理行为：搜 "Amy Madigan spouse" → 没找到 → 放弃
- 输出：*"The documents do NOT contain information about Amy Madigan's spouse"*

**案例 C：48.8% 就在眼前**

- 任务：Nigeria 穆斯林人口比例？
- 答案：**48.8 percent**（文档中明确写着的统计数据）
- 子代理行为：搜 "Matthew 24:24 Pew Research Nigeria" → 没找到
- 输出：*"Matthew 24:24: Not found in this document"*

### 根因：9B 模型的搜索策略缺陷

- grep 关键词选错 → 没命中 → 放弃
- 不会换关键词重试
- 不会逐段扫描未匹配区域
- 不会扩大搜索范围

## 7. 没 Spawn 的时候：62.5% 失败率

### 整体数据

| | Spawn了 (163题) | 没Spawn (32题) |
|---|---|---|
| 准确率 | 46% | **37%** |
| 完全闲置 | 0% | 10% |

### 四种失败模式

| 模式 | 占比 | 准确率 | 典型输出 |
|------|------|--------|----------|
| 🟠 对话模式 | ~40% | 0% | *"I'll read that file for you."* → 不动手 |
| 🟠 文件系统迷路 | ~30% | ~20% | ls/find/pwd 转圈，找不到 documents.txt |
| 🟡 读了但推理错 | ~20% | ~50% | 读到了但理解偏差 |
| 🟡 完全闲置 | ~10% | 0% | 空输出，MUST 把自己搞懵了 |

**对话模式是最离谱的一类**：模型把实验 prompt 当成用户发来的聊天消息，回复 "What would you like me to do with this information?" 然后等用户回应——而用户是实验系统，永远不会回应。

## 8. MUST 悖论：逼出来的 spawn 不如不做

| | v26-free (无 MUST) | v26-must (有 MUST) |
|---|---|---|
| Spawn 率 | **0%** | **84%** |
| 准确率 | **80%** | 45.1% |
| 闲置率 | 0% | 6% |
| 策略 | 全部直接读 | 84% spawn + 59% 读 + 49% 双管 |

### v26-must 策略矩阵

| 策略 | 题数 | 准确率 |
|------|------|--------|
| 只直接读，不 spawn | 20 | **60%** ← 最高 |
| 只 spawn，不直接读 | 68 | 47% |
| 双管齐下（读+spawn） | 95 | 46% |
| 什么都不做 | 12 | 0% |

**结论**：在当前设置下，最优策略是**单 Agent 直接读文档**（60% 准确率），不需要 spawn。

## 10. 结论与开放问题

### 核心结论

1. **Qwen3.5-9B 绝不会自愿 spawn**：v26-free 中 195 题 0% spawn，默认策略是直接读

2. **Multi-Agent 收益取决于分工类型**：
   - 推理分工（v21）：子代理只做推理 → **+10.6pp**
   - 检索分工（v26）：子代理做检索 → **-4pp**

3. **检索是瓶颈，不是上下文窗口**：24 次 "not found" 100% 是检索失败，0 次真正缺失。文档最大 13K tokens，远低于 65K 窗口。

4. **MUST 悖论**：强制 spawn 能把 spawn 率从 0% 推到 84%，但准确率从 80% 降到 45%

5. **当前最优策略**：单 Agent 直接读（60%），不需要 spawn

### 开放问题

1. **换更强的子代理模型能否逆转检索分工的负面效果？** 换 Qwen3.5-27B 或更大的模型做子代理，检索能力会提升吗？

2. **异构分工是否更优？** 9B 主代理（推理）+ 0.5B 子代理（只做 grep）vs 反过来？

3. **这个发现能推广到其他 benchmark 吗？** 目前只在 MuSiQue 多跳QA上验证。

4. **如果子代理不返回纯文本而是结构化结果（JSON），整合失败率会降低吗？**
