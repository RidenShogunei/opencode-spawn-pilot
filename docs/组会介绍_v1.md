## 1. 研究背景与动机

### 1.1 Task Delegation 的核心问题

Multi-Agent 协作中，**什么时候该委托（When to Delegate）、怎么委托（How to Delegate）、怎么用委托结果（How to Use Results）** 才是真正的核心问题：

```
什么时候委托？
  ├── 问题太复杂，一个模型处理不过来？
  ├── 模型自己搜不到，需要专门的搜索 agent？
  └── 任务可以并行，同时委托给多个 subagent？

怎么委托？
  ├── prompt 怎么写，描述要有多具体？
  ├── 要不要给 subagent 指定搜索范围？
  └── 委托出去的范围和主模型保留的范围怎么划分？

怎么用结果？
  ├── subagent 返回的纯文本，主模型怎么提取关键信息？
  ├── subagent 找错了方向，主模型怎么修正？
  └── 多轮委托时，上下文怎么累积和整合？
```

**已有研究的问题**：大多数工作假设"spawn 就能提升"，但从未系统研究过 Agent **自己** 是否知道如何正确地委托。

### 1.2 本研究目标

1. **核心问题**：Agent 什么时候该 spawn、怎么 spawn、spawn 完之后怎么用？
2. 对比 Single Agent vs Force-Multi（强制委托）在不同复杂度任务上的表现
3. 分析 spawn 机制在不同复杂度任务（2/3/4 hop）上的效果差异
4. 找出瓶颈：是 spawn 机制的问题，还是 Agent 委托能力的问题？

## 2. 相关工作

### 2.1 Multi-Agent 协作框架

| 框架 | 特点 | 代表工作 |
|------|------|---------|
| LangChain Agent | 工具调用 + 记忆 | ReAct, Self-Ask |
| AutoGPT / BabyAGI | 自主任务分解 | 任务链式执行 |
| CrewAI | Role-based 多 Agent | 角色分工协作 |
| OpenCode | 代码搜索 + Agent 工具 | 代码理解任务 |
| Model Scope Agent | LLM + 工具生态 | 通用任务 |

### 2.2 OpenCode 的 Task Delegation 机制

- 内置 `task` 工具允许主 Agent spawn 独立子 Agent
- 子 Agent 只能使用 GlobTool / GrepTool / LS / View（只读工具）
- 每个子 Agent 调用是 **无状态** 的
- **关键问题**：主 Agent 能否正确地使用这个机制？

## 3. 实验设计

### 3.1 什么是 "Hop"（跳数）？

**Hop 是指多跳问答中需要多少步推理才能找到答案。**

```
1-hop：直接搜索即可得到答案
  问题：北京是哪国首都？→ 搜索"北京" → 直接得到"中国"
  
2-hop：需要两步推理
  问题：A 的邻居是谁？
  步骤1：搜索 A → 得到 B（朋友）
  步骤2：搜索 B → 得到 C（答案）
  
3-hop：需要三步推理
  问题：A 通过 B 连接到哪个城市？
  步骤1：搜索 A → 得到 B（公司）
  步骤2：搜索 B → 得到 C（城市）
  步骤3：搜索 C → 得到 D（答案）
  
4-hop：以此类推
```

Hop 数越多，推理链越长，上下文记忆压力越大，spawn 的潜在价值越高。

### 3.2 两种 Agent 协作模式

```
┌─────────────────────────────────────────────────────────┐
│                    Single Agent                          │
│  模型独立完成所有搜索 + 推理，无委托                      │
└─────────────────────────────────────────────────────────┘

┌─────────────────────────────────────────────────────────┐
│               Force-Multi (强制多 Agent)                 │
│  每次工具调用都强制通过 task 工具 spawn subagent         │
│  prompt："你必须使用 task 工具搜索文档"                  │
└─────────────────────────────────────────────────────────┘
```

### 3.3 评估指标

| 指标 | 定义 |
|------|------|
| **Accuracy** | 正确回答数 / 总题数 |
| **Spawn Rate** | 模型 spawn subagent 的比例 |
| **Spawn Accuracy** | spawn 的任务中正确回答的比例 |

### 3.4 核心假设

- **H1**：Hop 数越高，spawn 的潜在收益越大（搜索空间更大，更需要并行或专门搜索）
- **H2**：如果 spawn 后准确率仍低，说明瓶颈在 Agent 的**委托能力**，而非 spawn 机制本身
- **H3**：简单任务（2-hop）spawn 可能有害，因为委托开销超过收益

## 4. OpenCode 工具架构

### 4.1 工具层次

```
Main Model (Qwen3.5-9B)
    │
    ├── Bash / Edit / Replace / View / Glob / Grep
    │   (直接执行，原生工具体验)
    │
    └── Agent tool (task 委托)
            │
            └── Subagent Model (独立 Qwen3.5-9B 实例)

                    ├── GlobTool (只读)
                    ├── GrepTool (只读)
                    ├── LS (只读)
                    └── View (只读)
```

**关键限制**：Subagent 无法使用 Bash/Edit/Replace，只能搜索和读取。

## 6. 实验结果

### 6.1 总体结果

| 模式 | 准确率 | Spawn 率 |
|------|--------|----------|
| **Single Agent** | **23/55 (41.8%)** | 0% |
| **v14 Force-Multi（baseline）** | 22/55 (40.0%) | 33/55 (60%) |
| **v13 Force-Multi（Deliberation）** | 25/55 (45.5%) 人工 | 33/55 (60%) |

> v13 的 45.5% 为人工逐题核查结果（自动评测有 bug），Deliberation 提示词使准确率提升约 5.5%。

**结论**：Multi 与 Single 基本持平，净效果 Multi 输 1 题。

### 6.2 Per-Hop 准确率（v14 vs Single）

| Hop | 题数 | Single | v14 Multi | 胜负 |
|-----|------|--------|-----------|------|
| 2-hop | 20 | 35% (7/20) | **50%** (10/20) | Multi +3 |
| 3-hop | 15 | 40% (6/15) | **53%** (8/15) | Multi +3 |
| 4-hop | 14 | **36%** (5/14) | 21% (3/14) | Single +4 |
| Hotpot (2-hop) | 6 | **83%** (5/6) | 17% (1/6) | Single +4 |

**观察**：
- 2-hop 和 3-hop：Multi 略优于 Single
- 4-hop 和 Hotpot：Single 显著优于 Multi
- Hotpot 是 Multi 最大的失败场景（Single 对 5 题，Multi 只对 1 题）

### 6.3 胜负详细分析

| 类别 | 数量 |
|------|------|
| Multi 靠 Spawn 赢了（spawn 且答对，Single 答错） | **10** |
| Multi 没 Spawn 但巧合赢了（Multi 答对，Single 答错） | **5** |
| Multi Spawn 了但仍输（spawn 了但答错，Single 答对） | **6** |
| Multi 没 Spawn 导致输（Multi 答错，Single 答对） | **9** |
| **净效果** | **-1**（Multi 净输 1 题） |

### 6.4 具体任务示例

#### 示例 1：Spawn 帮助了（Multi 对，Single 错）

**任务**：`musique_2hop__642686_7292`
**问题**：Smooth Jazz Stations 节目第三位艺术家是谁？
**标准答案**：George Benson

| 模式 | 预测 | 结果 |
|------|------|------|
| Single | "The question asks: Along with Kenny G and the performer of Hello Tomorrow..." | ❌ |
| Multi（spawn=True） | "The third artist featured on Smooth Jazz Stations is George Benson." | ✅ |

**任务**：`musique_4hop1__88342_49853_128008_89859`

**标准答案**：March 29, 2018

## 7. 结果分析

### 7.1 为什么 2-hop 和 3-hop Multi 略好？

MuSiQue 的 2-hop 和 3-hop 任务中，spawn 帮助主模型：
- 减少了自己搜索的工作量
- subagent 专门负责读文档，主模型负责推理

但提升幅度有限（+3 题），不足以证明 spawn 机制真正有效。

### 7.2 为什么 4-hop 和 Hotpot Multi 显著更差？

**4-hop**：推理链太长（4 步），spawn-return 循环每多一次，上下文错误累积的概率增加。subagent 的 Glob/Grep/LS/View 工具集太弱，无法支撑 4 步推理链。

**Hotpot**：Multi 的输出捕获出现了问题（部分任务 0 字节输出），导致准确率极低。这是工程问题，不是 spawn 机制的问题。

### 7.3 为什么 Deliberation 提示词有效？

v13 增加了"先思考再 spawn"步骤：
```
First, read the question and think about what information is needed and where to find it
```

这让模型在 spawn 前多了一步**规划**，减少了"不假思索就委托"的现象。

## 8. 核心发现：Agent 的 Task Delegation 能力

> **这是本研究最重要的发现。**
> 
> Force-Multi 的本质是"强制一个还没学会 delegation 的模型去 delegation"。我们发现 **Agent 根本不知道什么时候该委托、怎么委托、以及如何整合结果**。这不是 spawn 机制的问题，而是 Agent 本身的能力问题。

### 8.1 三种典型的 Delegation 病态行为

我们从实验日志中识别出三类典型问题：

#### 病态 1：过早委托（Premature Delegation）

**主模型还没想清楚要搜什么、怎么搜，就急着把任务甩给 subagent。**

真实案例（`musique_2hop__642686_7292`）：
```
问题：Along with Kenny G and the performer of Hello Tomorrow, 
      what artist was featured on Smooth Jazz Stations?

spawn 的 prompt：
  description: "Search smooth jazz and artists"
  prompt: "Along with Kenny G and the performer of Hello Tomorrow, 
           what artist was featured on Smooth Jazz Stations?"
```

模型把**原封不动的问题**作为 subagent 的 prompt，连自己都没想清楚要搜什么。正确的做法应该是：先分析问题 → 确定搜索关键词 → 明确告诉 subagent 去哪个段落找。

#### 病态 2：过度委托（Redundant Delegation）

**问题已经快要解出，或者文档里已经有明确答案，模型仍然要 spawn 一下。**

真实案例（`musique_2hop__21104_16335`）：
```
问题：The group representing at least 70% of Jews worldwide and 
      Italians may be genetically similar due to what two factors?

Single 预测："The group representing at least 70% of Jews worldwide 
             is Ashkenazi Jews, and the Italians..."
Multi 预测："2. Shared southern European admixture - Ashkenazi and 
            Sephardic Jews show non-Je..."

标准答案：inter-marriage and conversions in the time of the Roman Empire
```

Single 实际上**已经找到了正确的答案方向**（Ashkenazi Jews），但 Multi 仍然 spawn，结果 subagent 找到了"genetic admixture"相关内容，主模型把它整合成了"Shared southern European admixture"这个错误答案。

**过度委托的代价**：spawn 把主模型从正确的推理路径上拉走了。

#### 病态 3：工具盲目（Tool Blindness）

**主模型没有强制 subagent 使用任何工具，也没有指定要搜索的具体段落。**

真实案例：
```
spawn 的 prompt：
  description: "Search for César Gaytan birthplace"
  prompt: "Read the provided documents and find where César Gaytan was born 
           (which continent). Provide specific information about his birthplace."
```

prompt 里没有告诉 subagent 去哪个段落找，只说"读提供的文档"。subagent 实际用 Glob/Grep/LS/View 工具在文档中搜索，但主模型无法控制它的搜索路径。

**工具盲目的后果**：subagent 可能读了错误的文档，或者用低效的方式搜索，主模型一无所知。

#### 病态 4：结果整合失败（Integration Failure）

**即使 subagent 返回了正确信息，主模型也整合错了。**

真实案例（`musique_4hop1__88342_49853_128008_89859`）：
```
问题：When did the 2018 Major League Baseball season begin?

标准答案：March 29, 2018

Single：'"The 2018 Major League Baseball season began on March 29, 2018..."'  → ✅
Multi： "4. MLB regular season typically begins in late March 
         (currently March 29) and runs..."  → ❌
```

subagent 找到了正确的日期（March 29, 2018），但主模型的整合出了问题——把"began on March 29"改成了"typically begins in late March (currently March 29)"，加了自己的推理（"typically"），引入了错误。

### 8.2 这些病态行为说明了什么？

| 病态类型 | 核心问题 | 对准确率的影响 |
|----------|----------|----------------|
| 过早委托 | 问题还没理解就委托，subagent 搜索方向可能偏了 | 主模型被错误信息误导 |
| 过度委托 | 简单问题也要走完整 spawn-return 链 | 把主模型从正确路径上拉走 |
| 工具盲目 | subagent 搜不到关键信息，主模型不知道 | 看似 spawn 了，实际没解决问题 |
| 整合失败 | subagent 返回了正确信息，主模型整合错了 | spawn 收益被整合损耗抵消 |

### 8.3 核心结论

**Force-Multi 在当前模型上整体无效甚至有害，根本原因不是 spawn 机制本身，而是 Agent 的 delegation 能力不足。**

```
Agent 能力不足的具体表现：
  ✗ 不知道什么时候该委托（过早/过度委托）
  ✗ 不知道怎么委托（prompt 质量差，工具盲目）
  ✗ 不知道怎么用结果（整合失败）

spawn 机制的损失：
  - 委托出去的信息可能不完整或不准确
  - 即使 subagent 返回了正确信息，主模型也可能整合错
  - 简单任务的委托开销 > 委托收益
```

### 8.4 如何改进 Agent 的 Delegation 能力？

从实验结果看，**Deliberation 提示词**（先思考再委托）是目前最简单有效的改进方向：

- v13（加了 Deliberation）比 v14（baseline）高 5.5%
- spawn 率不变（都是 60%），但 spawn 后准确率提升

这说明：**让模型在委托前多一步"规划"，可以减少过早委托和过度委托**。

未来还可以：
1. **结构化委托**：强制要求 subagent 返回 JSON 格式的结果，而不是纯文本
2. **显式推理**：要求主模型在 spawn 前写出推理步骤
3. **异构模型**：小模型做搜索，大模型做推理，减少整合损耗

## 9. 结论

### 9.1 核心结论

1. **Multi Agent 与 Single Agent 基本持平**：22/55 vs 23/55，净效果 Multi 输 1 题。

2. **Hop 数的影响不明确**：2-hop 和 3-hop Multi 略好，4-hop Single 更好，原因可能是任务本身特性而非 hop 数。

3. **Agent 不知道如何正确委托**：过早委托、过度委托、工具盲目、整合失败——这是 Agent 能力问题，不是 spawn 机制问题。

4. **Deliberation 提示词有效**：让模型先思考再委托，可以减少无效委托。

5. **瓶颈在 Agent 能力，而非 spawn 机制**：subagent 找到了正确信息，主模型仍然推理错误。

### 9.2 与已有预期的对比

| 预期 | 实际 |
|------|------|
| Multi Agent 应该更好 | 基本持平，收益被无效委托抵消 |
| 复杂任务（高 hop）spawn 受益更多 | 4-hop 反而 Single 更好 |
| 模型会主动 spawn | 强制模式下也只有 60% spawn |

---

## 10. 未来工作

### 10.1 改进 Agent 的 Delegation 能力

1. **结构化委托格式**：强制 subagent 返回 JSON，主模型更容易提取信息
2. **显式推理链**：要求主模型在 spawn 前写出推理步骤
3. **多轮 Deliberation**：先思考（分析问题）→ 再规划（确定搜索策略）→ 再委托

### 10.2 异构模型组合

- Subagent 使用更小的 specialized 模型（如 Qwen2.5-0.5B 做搜索）
- Main model 使用更大的模型（如 Qwen3.5-9B 做推理）

### 10.3 更复杂的多跳基准

MuSiQue 的 hop 数有限，可以测试 hop 数更高（5-hop+）的任务，看 spawn 机制是否在更复杂场景下效果更好。
