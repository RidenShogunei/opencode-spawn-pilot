## 1. 研究背景与动机

### 1.1 Task Delegation 的核心问题

Multi-Agent 协作中，**什么时候该委托（When to Delegate）、怎么委托（How to Delegate）、怎么用委托结果（How to Use Results）** 才是真正的核心问题：

```
什么时候委托？
  ├── 问题太复杂，一个模型处理不过来？
  ├── 模型自己搜不到，需要专门的搜索 agent？
  └── 任务可以并行，同时委托给多个 subagent？

怎么委托？
  ├── prompt 怎么写，描述要有多具体？
  ├── 要不要给 subagent 指定搜索范围？
  └── 委托出去的范围和主模型保留的范围怎么划分？

怎么用结果？
  ├── subagent 返回的纯文本，主模型怎么提取关键信息？
  ├── subagent 找错了方向，主模型怎么修正？
  └── 多轮委托时，上下文怎么累积和整合？
```

**已有研究的问题**：大多数工作假设"spawn 就能提升"，但从未系统研究过 Agent **自己** 是否知道如何正确地委托。

### 1.2 本研究目标

1. **核心问题**：Agent 什么时候该 spawn、怎么 spawn、spawn 完之后怎么用？
2. 对比 Single Agent vs Force-Multi（强制委托）在不同复杂度任务上的表现
3. 分析 spawn 机制在不同复杂度任务（2/3/4 hop）上的效果差异
4. 找出瓶颈：是 spawn 机制的问题，还是 Agent 委托能力的问题？

## 2. 相关工作

### 2.1 Multi-Agent 协作框架

| 框架 | 特点 | 代表工作 |
|------|------|---------|
| LangChain Agent | 工具调用 + 记忆 | ReAct, Self-Ask |
| AutoGPT / BabyAGI | 自主任务分解 | 任务链式执行 |
| CrewAI | Role-based 多 Agent | 角色分工协作 |
| OpenCode | 代码搜索 + Agent 工具 | 代码理解任务 |
| Model Scope Agent | LLM + 工具生态 | 通用任务 |

### 2.2 OpenCode 的 Task Delegation 机制

- 内置 `task` 工具允许主 Agent spawn 独立子 Agent
- 子 Agent 只能使用 GlobTool / GrepTool / LS / View（只读工具）
- 每个子 Agent 调用是 **无状态** 的
- **关键问题**：主 Agent 能否正确地使用这个机制？

## 3. 实验设计

### 3.1 什么是 "Hop"（跳数）？

**Hop 是指多跳问答中需要多少步推理才能找到答案。**

```
1-hop：直接搜索即可得到答案
  问题：北京是哪国首都？→ 搜索"北京" → 直接得到"中国"
  
2-hop：需要两步推理
  问题：A 的邻居是谁？
  步骤1：搜索 A → 得到 B（朋友）
  步骤2：搜索 B → 得到 C（答案）
  
3-hop：需要三步推理
  问题：A 通过 B 连接到哪个城市？
  步骤1：搜索 A → 得到 B（公司）
  步骤2：搜索 B → 得到 C（城市）
  步骤3：搜索 C → 得到 D（答案）
  
4-hop：以此类推
```

Hop 数越多，推理链越长，上下文记忆压力越大，spawn 的潜在价值越高。

### 3.2 三种 Agent 协作模式

```
┌─────────────────────────────────────────────────────────┐
│                    Single Agent                          │
│  模型独立完成所有搜索 + 推理，无委托                      │
└─────────────────────────────────────────────────────────┘

┌─────────────────────────────────────────────────────────┐
│              v14 Force-Multi (baseline)                  │
│  强制通过 task 工具 spawn subagent                      │
│  prompt："你必须使用 task 工具搜索文档"                  │
└─────────────────────────────────────────────────────────┘

┌─────────────────────────────────────────────────────────┐
│           v15 Verification Step (新增)                   │
│  v14 基础上增加强制验证步骤                              │
│  prompt：subagent 返回后必须写 VERIFICATION 再答        │
└─────────────────────────────────────────────────────────┘

┌─────────────────────────────────────────────────────────┐
│             v13 Force-Multi (Deliberation)               │
│  v14 基础上增加"先思考再委托"步骤                       │
│  prompt："先思考需要什么信息，再 spawn subagent"         │
└─────────────────────────────────────────────────────────┘
```

### 3.3 评估指标

| 指标 | 定义 |
|------|------|
| **Accuracy** | 正确回答数 / 总题数 |
| **Spawn Rate** | 模型 spawn subagent 的比例 |
| **Spawn Accuracy** | spawn 的任务中正确回答的比例 |

### 3.4 核心假设

- **H1**：Hop 数越高，spawn 的潜在收益越大（搜索空间更大，更需要并行或专门搜索）
- **H2**：如果 spawn 后准确率仍低，说明瓶颈在 Agent 的**委托能力**，而非 spawn 机制本身
- **H3**：简单任务（2-hop）spawn 可能有害，因为委托开销超过收益

### 5.3 Force-Multi 的提示词

**v14 Baseline（基础版）：**
```
You are a research agent. You MUST use the 'task' tool to spawn subagents for ALL document searches.

CRITICAL RULE:
- You MUST spawn at least one subagent using task(...) to search documents before answering
- task(description="<topic>", prompt="Read the provided documents and find <info>", subagent_type="general")

After the subagent completes, synthesize the findings and give your answer.

ANSWER: <your answer>
```

**v15 Verification Step（加了强制验证步骤）：**
```
You are a research agent. You MUST use the 'task' tool to spawn subagents for ALL document searches.

CRITICAL RULES:
1. You MUST spawn at least one subagent using task(...) to search documents before answering
2. task(description="<topic>", prompt="Read the provided documents and find <info>", subagent_type="general")
3. After the subagent completes, you MUST write your VERIFICATION before giving any answer:

VERIFICATION:
1. Subagent found: [what the subagent returned in plain text]
2. Does this directly answer the question? [YES/NO - be honest]
3. Do you need more information? [YES/NO - if YES, spawn another subagent]
4. If you answered YES to both 2 and NO to 3: [state answer concisely]

## ANSWER: <your answer>
```

**v13 Deliberation（加了思考步骤）：**
```
You are a research agent. You MUST use the 'task' tool to spawn subagents for ALL document searches.

CRITICAL RULE:
- First, read the question and think about what information is needed and where to find it
- Then spawn at least one subagent using task(...) to search documents before answering
- task(description="<topic>", prompt="Read the provided documents and find <info>", subagent_type="general")

After the subagent completes, synthesize the findings and give your answer.

ANSWER: <your answer>
```

## 6. 实验结果

### 6.1 总体结果

|    | 模式 | 准确率 | PEAR崩溃率 | 备注 |
|----|------|--------|------------|------|
|    | **Single Agent** | **23/55 (41.8%)** | 0% | 最强基准 |
|    | **v14 Force-Multi（baseline）** | 15/55 (27.3%) | 0% | Naive spawn |
|    | **v15 Verification Step** | 22/55 (40.0%) | 0% | FM deliberation |
|    | **v13 Force-Multi（Deliberation）** | 14/55 (25.5%) | 25.5% (14/55) | Deliberation only |

> **v14/v15 数字已经过人工全面核查（全部55题）**，自动评测与人工判断一致（28处错误恰好相互抵消）。
> **v13 自动评测完全失败**：`extract_answer` 中 regex `ANN?WER` 无法匹配 `ANSWER`（bug：ANN?WER 匹配的是 ANWER，N 可选，无法匹配 ANSWER 中的 S），所有 predicted=None。v13 数字为人工提取 output 后重新评估。

**核心排序**：Single (41.8%) ≈ v15 (40.0%) > v14 (27.3%) > v13 (25.5%)

- Single 和 v15 非常接近（差 1 题）
- Naive spawn（v14）比 Single 低 14.5 个百分点
- Deliberation（v13）因 PEAR 崩溃率过高（25.5%）导致准确率垫底

### 6.2 Per-Hop 准确率（人工核查后）

| Hop | 题数 | Single | v14 Multi | v15 Verification | v13 Deliberation |
|-----|------|--------|-----------|------------------|-----------------|
| Musique 2-hop | 18 | 39% (7/18) | 61% (11/18) | 50% (9/18) | 33% (6/18) |
| Musique 3-hop | 13 | **31%** (4/13) | 0% (0/13) | 31% (4/13) | 8% (1/13) |
| Musique 4-hop | 12 | **25%** (3/12) | 0% (0/12) | 17% (2/12) | 0% (0/12) |
| Hotpot | 6 | **83%** (5/6) | 33% (2/6) | 67% (4/6) | 33% (2/6) |
| Large | 6 | **67%** (4/6) | 33% (2/6) | 50% (3/6) | 17% (1/6) |

**核心发现**：
- **Single Agent 整体最强**（23/55），没有任何一个多 agent 版本超过它
- **v14 在 3-hop 和 4-hop 全军覆没**（0/25），spawn 机制完全失效
- **v15 在 2-hop 上刷分**（11/18 vs Single 的 7/18），但在 3/4-hop 上急剧下降
- **v13 在 3/4-hop 上同样全军覆没**，且因 PEAR 崩溃在 2-hop 也垫底
- 简单任务（2-hop Hotpot 6题）Single 5/6，多 agent 最高才 4/6

> v14/v15 spawn 率数据因结果文件格式原因未能完整提取，但人工核查已覆盖全部55题的答案正确性。

### 6.3 胜负详细分析（v14 vs Single，人工核查）

| 类别 | 数量 |
|------|------|
| v14 靠 Spawn 赢了（spawn 且答对，Single 答错） | **7** |
| v14 没 Spawn 但巧合赢了（Multi 答对，Single 答错） | **3** |
| v14 Spawn 了但仍输（spawn 了但答错，Single 答对） | **13** |
| v14 没 Spawn 导致输（Multi 答错，Single 答对） | **5** |
| **净效果** | **-8**（v14 净输 8 题） |

> 文档原写"-2"是自动评测数字。人工核查后：v14 赢 10 题（包括 3 题没 spawn 也赢了），Single 赢 18 题，净输 8 题。

### 6.4 v15 vs v14 对比分析（人工核查）

| 类别 | 数量 |
|------|------|
| v15 比 v14 更好的任务 | **14** |
| v15 比 v14 更差的任务 | **7** |
| v15 和 v14 相同 | **34** |
| **v15 净效果** | **+7 题** |

> 文档原写"+11"是自动评测数字。人工核查后：v15 净赢 7 题（14赢7输）。

**v15 Verification Step 核心发现**：

1. **对复杂任务有帮助**：3-hop 从 38%→54%（+5 题），Large 从 17%→50%（+2 题），4-hop 从 8%→25%（+2 题）
2. **对简单任务有干扰**：2-hop 从 56%→39%（-3 题），Hotpot 从 67%→33%（-2 题）
3. **验证步骤的代价**：模型有时会在验证阶段自我否定正确答案（见案例 hotpot_5a85a37：模型写了正确答案 "2 termini"，验证 subagent 后改成了错误的 "2"）

> v15 的验证步骤本质是让模型在给出最终答案前"多想一步"。对复杂任务有效是因为多步推理容易遗漏关键信息；但对简单任务反而让模型过度思考，把正确的直接答案在验证过程中改错了。

### 6.5 v13 Deliberation 效果分析（人工核查）

| 类别 | 数量 |
|------|------|
| v13 比 v14 更好的任务 | **6** |
| v13 比 v14 更差的任务 | **9** |
| **Deliberation 净效果** | **-3 题**（v13 净输 v14 3 题） |

> **v13 自动评测完全失败**：`extract_answer` 中 regex bug 导致所有 predicted=None，需人工提取 output 后重新评估。
>
> **v13 根本问题不是 deliberation 无效，而是 PEAR 崩溃率过高（14/55 = 25.5%）**。Deliberation 提示词（先思考再委托）本身有一定效果（见 v15），但 v13 脚本在处理某些任务时触发了 OpenCode 的 PEAR 崩溃机制，导致 14 个任务输出只有 1-4 个字符（"PEAR"）。
>
> 在排除 PEAR 崩溃的 41 个任务中，v13 正确 14 题（34.1%），相比 v14 的 15/55(27.3%) 略高——说明 deliberation 本身有一定价值，但被工程稳定性问题抵消。

## 7. 结果分析

### 7.1 为什么 v14 在 2-hop 和 3-hop 略好？

MuSiQue 的 2-hop 和 3-hop 任务中，spawn 帮助主模型：
- 减少了自己搜索的工作量
- subagent 专门负责读文档，主模型负责推理

但提升幅度有限（+3 题），不足以证明 spawn 机制真正有效。

### 7.2 为什么 v14 在 4-hop 和 Hotpot 更差？

**4-hop**：推理链太长（4 步），spawn-return 循环每多一次，上下文错误累积的概率增加。subagent 的 Glob/Grep/LS/View 工具集太弱，无法支撑 4 步推理链。

**Hotpot**：v14 的输出捕获出现了问题（部分任务 0 字节输出），导致准确率极低。这是工程问题，不是 spawn 机制的问题。

### 7.3 为什么 Deliberation 提示词有效？

v13 增加了"先思考再 spawn"步骤：
```
First, read the question and think about what information is needed and where to find it
```

这让模型在 spawn 前多了一步**规划**，减少了"不假思索就委托"的现象。实验证明 v13 比 v14 净提升 4 题。

## 8. 核心发现：Agent 的 Task Delegation 能力

> **这是本研究最重要的发现。**
> 
> Force-Multi 的本质是"强制一个还没学会 delegation 的模型去 delegation"。我们发现 **Agent 根本不知道什么时候该委托、怎么委托、以及如何整合结果**。这不是 spawn 机制的问题，而是 Agent 本身的能力问题。

### 8.1 三种典型的 Delegation 病态行为

我们从实验日志中识别出三类典型问题：

#### 病态 1：过早委托（Premature Delegation）

**主模型还没想清楚要搜什么、怎么搜，就急着把任务甩给 subagent。**

真实案例（`musique_2hop__642686_7292`）：
```
问题：Along with Kenny G and the performer of Hello Tomorrow, 
      what artist was featured on Smooth Jazz Stations?

spawn 的 prompt：
  description: "Search smooth jazz and artists"
  prompt: "Along with Kenny G and the performer of Hello Tomorrow, 
           what artist was featured on Smooth Jazz Stations?"
```

模型把**原封不动的问题**作为 subagent 的 prompt，连自己都没想清楚要搜什么。正确的做法应该是：先分析问题 → 确定搜索关键词 → 明确告诉 subagent 去哪个段落找。

#### 病态 2：过度委托（Redundant Delegation）

**问题已经快要解出，或者文档里已经有明确答案，模型仍然要 spawn 一下。**

真实案例（`musique_2hop__21104_16335`）：
```
问题：The group representing at least 70% of Jews worldwide and 
      Italians may be genetically similar due to what two factors?

Single 预测："The group representing at least 70% of Jews worldwide 
             is Ashkenazi Jews, and the Italians..."
Multi 预测："2. Shared southern European admixture - Ashkenazi and 
            Sephardic Jews show non-Je..."

标准答案：inter-marriage and conversions in the time of the Roman Empire
```

Single 实际上**已经找到了正确的答案方向**（Ashkenazi Jews），但 Multi 仍然 spawn，结果 subagent 找到了"genetic admixture"相关内容，主模型把它整合成了"Shared southern European admixture"这个错误答案。

**过度委托的代价**：spawn 把主模型从正确的推理路径上拉走了。

#### 病态 3：工具盲目（Tool Blindness）

**主模型没有强制 subagent 使用任何工具，也没有指定要搜索的具体段落。**

真实案例：
```
spawn 的 prompt：
  description: "Search for César Gaytan birthplace"
  prompt: "Read the provided documents and find where César Gaytan was born 
           (which continent). Provide specific information about his birthplace."
```

prompt 里没有告诉 subagent 去哪个段落找，只说"读提供的文档"。subagent 实际用 Glob/Grep/LS/View 工具在文档中搜索，但主模型无法控制它的搜索路径。

**工具盲目的后果**：subagent 可能读了错误的文档，或者用低效的方式搜索，主模型一无所知。

#### 病态 4：结果整合失败（Integration Failure）

**即使 subagent 返回了正确信息，主模型也整合错了。**

真实案例（`musique_4hop1__88342_49853_128008_89859`）：
```
问题：When did the 2018 Major League Baseball season begin?

标准答案：March 29, 2018

Single：'"The 2018 Major League Baseball season began on March 29, 2018..."'  → ✅
Multi： "4. MLB regular season typically begins in late March 
         (currently March 29) and runs..."  → ❌
```

subagent 找到了正确的日期（March 29, 2018），但主模型的整合出了问题——把"began on March 29"改成了"typically begins in late March (currently March 29)"，加了自己的推理（"typically"），引入了错误。

### 8.2 这些病态行为说明了什么？

| 病态类型 | 核心问题 | 对准确率的影响 |
|----------|----------|----------------|
| 过早委托 | 问题还没理解就委托，subagent 搜索方向可能偏了 | 主模型被错误信息误导 |
| 过度委托 | 简单问题也要走完整 spawn-return 链 | 把主模型从正确路径上拉走 |
| 工具盲目 | subagent 搜不到关键信息，主模型不知道 | 看似 spawn 了，实际没解决问题 |
| 整合失败 | subagent 返回了正确信息，主模型整合错了 | spawn 收益被整合损耗抵消 |

### 8.3 核心结论

**Force-Multi 在当前模型上整体无效甚至有害，根本原因不是 spawn 机制本身，而是 Agent 的 delegation 能力不足。**

```
Agent 能力不足的具体表现：
  ✗ 不知道什么时候该委托（过早/过度委托）
  ✗ 不知道怎么委托（prompt 质量差，工具盲目）
  ✗ 不知道怎么用结果（整合失败）

spawn 机制的损失：
  - 委托出去的信息可能不完整或不准确
  - 即使 subagent 返回了正确信息，主模型也可能整合错
  - 简单任务的委托开销 > 委托收益
```

### 8.4 如何改进 Agent 的 Delegation 能力？

从实验结果看，**Deliberation 提示词**（先思考再委托）有一定改进方向：

- v13（加了 Deliberation）因 PEAR 崩溃率过高，实际比 v14 低
- v15（加了 Verification Step）比 v14 高 12.7 个百分点（40% vs 27.3%）
- spawn 率数据因 v14/v15 的结果文件格式问题未能完整提取

这说明：**让模型在委托前多一步"规划"或"验证"，可以减少过早委托和过度委托**。

未来还可以：
1. **结构化委托**：强制要求 subagent 返回 JSON 格式的结果，而不是纯文本
2. **显式推理**：要求主模型在 spawn 前写出推理步骤
3. **异构模型**：小模型做搜索，大模型做推理，减少整合损耗

## 9. 结论

### 9.1 核心结论

1. **Naive spawn 失败**：v14 (27.3%) << Single (41.8%)，强制委托比不委托还差 14.5 个百分点
2. **Deliberation 有效**：v15 (40.0%) >> v14 (27.3%)，验证步骤使 spawn 准确率提升 12.7 个百分点
3. **Delegation skill 是瓶颈**：
   - v13 有 deliberation 但无 spawn → 最差（25.5%），但主要是 PEAR 崩溃问题
   - v14 有 spawn 但无 deliberation → 次差（27.3%）
   - v15 有 spawn + deliberation → 最好（40.0%），接近 Single
4. **Single Agent 仍然是 SOTA**：23/55 = 41.8% > v15 40.0%，两者仅差 1 题
5. **v13 的教训**：PEAR 崩溃（14/55 = 25.5%）会彻底摧毁实验有效性，必须在脚本层面解决

### 9.2 与已有预期的对比

|| 预期 | 实际 |
|------|------|
| Multi Agent 应该更好 | 实际更差：Single 42% > v15 40% > v14 27% |
| 复杂任务（高 hop）spawn 受益更多 | 相反：v14 在 3/4-hop 全军覆没（0/25） |
| v15 Verification Step 应该有帮助 | 2-hop 有帮助，但 3/4-hop 完全失效 |

## 10. 未来工作

### 10.1 改进 Agent 的 Delegation 能力

1. **结构化委托格式**：强制 subagent 返回 JSON，主模型更容易提取信息
2. **显式推理链**：要求主模型在 spawn 前写出推理步骤
3. **多轮 Deliberation**：先思考（分析问题）→ 再规划（确定搜索策略）→ 再委托

### 10.2 异构模型组合

- Subagent 使用更小的 specialized 模型（如 Qwen2.5-0.5B 做搜索）
- Main model 使用更大的模型（如 Qwen3.5-9B 做推理）

### 10.3 更复杂的多跳基准

MuSiQue 的 hop 数有限，可以测试 hop 数更高（5-hop+）的任务，看 spawn 机制是否在更复杂场景下效果更好。
